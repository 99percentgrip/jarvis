## Source audit and method

The Stage 7B plan and owning DOX, architecture, reports and evidence index were inspected. `release.yml` previously called `jarvis_release_candidate.py` to assemble an archive with the Stage 6 `jarvis_package.py` packer, then uploaded it directly. `platform-foundation.yml` separately called `test_native_package_install.py`, which repacked debug fixture binaries and, on Windows, constructed its own synthetic archive. Those installed packages were *not* the candidate archive. The wrapper and existing package/installer validators were reused; no independent packer or public publishing route was added.

Changed `.github/workflows/release.yml`, `scripts/jarvis_candidate_acceptance.py`, `scripts/test_jarvis_candidate_install.ps1`, `scripts/test_jarvis_candidate_acceptance.py`, `xtask/src/identity_naming.rs`, and owning DOX/architecture documentation. The native job checks canonical archive name, Stage 6 archive contents and manifest, exact SHA, compiler/lockfile, executable inventory/native headers, and the admitted tested browser archive digest and image ID. It installs the same archive in a private native runner root, exercises installed user-facing binaries and launchers, uninstalls and checks an unrelated sentinel, remeasures the original archive bytes, writes an acceptance receipt, and only then uploads that unchanged archive, checksum, provenance and receipt. Windows runs its actual installer and uninstaller; the runner-only script restores the user PATH even after failure. Review of PR #12 identified two acceptance gaps: installed TUI checks were only `--version`, and checksum/provenance bytes could change after validation. All five lanes now run the existing private signed-out first-launch and provider Settings terminal fixture against the installed TUI (Windows first installs pinned ConPTY requirements); the archive and both sidecars are snapshotted and remeasured after installation. A failed validation prevents upload. No local user installation is authorized.
