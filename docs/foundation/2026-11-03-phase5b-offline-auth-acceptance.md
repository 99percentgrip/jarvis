### Confirmed LM Studio defect, preserved failure and repair

Both production host implementations read an arbitrary JSON rejection body and formatted the full body into `ProviderError` on HTTP 401. A disposable loopback server echoed the synthetic `authorization: bearer synthetic-local-secret` value and a `private-server-message` in a 401 response. The **real session** regression `lmstudio_provider::selected_model_wire_tests::rejected_local_token_never_echoes_server_body_or_bearer` failed before repair in both hosts: `panicked ... provider echoed bearer` (TUI 1 failed/293 filtered; ACP 1 failed/62 filtered). A wrong initial `ToolChoiceIntent` import caused a compile error and was fixed before the red assertion; it is not product-failure evidence. The test's server accepts exactly one bounded request, verifies the outgoing bearer and echoes a canary. It asserts safe status, authentication category and no canary/body leak from the full error Debug representation.

Repair: the two host LM Studio session modules discard unread rejection bodies; classify status 401/403/429/404 separately with `http_status`, safe category and status-only message. Catalog discovery now refuses non-2xx **before** parsing untrusted JSON. This does not disable local auth or switch to anonymous billing. Focused post-repair receipts: `cargo test -p jarvis-tui --lib rejected_local_token_never_echoes_server_body_or_bearer` → `1 passed; 0 failed`; ACP equivalent → `1 passed; 0 failed`; `cargo test -p jarvis-tui --lib lmstudio_provider::selected_model_wire_tests` → `3 passed; 0 failed` (includes real local request and cancellation); ACP equivalent → `2 passed; 0 failed` (includes real local request). These are **in-process production-session** regressions, not an end-to-end LM Studio ACP/TUI process refusal test. CI/native checks for this new candidate remain pending until exact candidate publication.
