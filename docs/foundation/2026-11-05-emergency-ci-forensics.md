## Causal classification and repair assessment

- **Confirmed test-harness defect, already repaired in integrated main:** the earlier voice fixture allocated `samples * 20000` (~176 MiB) before writing the first stdout byte; on Intel this consumed the test's unchanged 10-second engine deadline before the 2 MiB output bound was encountered. Commit `a4fc5255` changed the fixture to stream 300 small sample chunks without allocating the oversized buffer. The assertion still requires `ResourceExhausted`; `tts_with` still uses 10 seconds and 2 MiB; production subprocess code was not changed. PR Intel ran successfully on the corrected source; locally on `a08b93d3`, `CARGO_BUILD_JOBS=2 CARGO_TARGET_DIR=/home/Alex/Projects/j%61rvis/.agent/phase5b-target cargo test --offline -p j%61rvis-voice --all-features --test pr2_tts oversized_output_is_resource_exhausted -- --test-threads=1` printed `test oversized_output_is_resource_exhausted ... ok` / `1 passed; 0 failed; 21 filtered out`. No additional source repair is justified for this already integrated defect. A green PR does not replace the cancelled merge-head native jobs.
- **External transport failure plus a confirmed CI resilience gap, not a product defect:** the ARM Docker build fetched snapshot-pinned packages but received upstream HTTP 503; amd64 build on the same main SHA succeeded, and the PR browser eventually passed after its failed first attempt. The same-SHA ARM recovery attempt failed again with 503/504 across many packages (see below), despite a different allocated runner and CDN IP; this is repository-side evidence of persistent transport failure, not proof of a global Debian incident. The original Dockerfile attempted the snapshot install once with neither bounded per-request retry nor whole-phase retry; temporary package retrieval errors made the entire mandatory browser job immediately red. A narrow **candidate** now retries the *same* signed snapshot acquisition without changing package versions, base digests or tests; fake-APT red/green proof establishes transient recovery and persistent fail-closed behavior, not actual recovery from the observed sustained upstream outage. Hosted two-architecture image acceptance remains required. No outage or native acceptance is declared resolved by local regression alone.
- **macOS cancellations / runner scheduling:** both main push jobs and the earlier Intel rerun were cancelled after ~15 minutes with no allocated runner and no steps. Workflow has `fail-fast: false`; main-push concurrency uses `run-<run_id>` and `cancel-in-progress` is false, so neither matrix fail-fast nor a newer main push via this workflow explains the cancellations. GitHub's [Actions and Pages incident](https://stspg.io/pjgptg3cfc6n) ran `16:05:31`–`17:01:11` and mentions delayed job status; it overlaps the later two cancellations but does not prove their exact origin. Earlier `15:19:19` cancellation predates that incident. GitHub's later [Actions incident](https://stspg.io/7pwv28hvkmz8) began `17:40:33` and cannot explain the `16:18` cancellations. No repository evidence establishes an actor, scheduler policy, capacity threshold or billing decision. Classify exact mechanism **UNKNOWN** and runner nonallocation **observed**. No speculative concurrency edit.
- **Resource/dependency audit:** native matrix labels are `macos-15-intel`, `macos-15`, `windows-2025`, `ubuntu-24.04` and `ubuntu-24.04-arm`; Intel/Windows 120-minute jobs, other jobs 90 minutes; failed mac jobs had no steps, so neither compilation resource pressure nor voice runtime executed there. Docker build uses digested base images, fixed snapshot and APT's normal integrity checking. `fail-fast: false`; checkout is exact PR head or push SHA; PR event and push have different SHA and independent runs and cache/runner conditions. No evidence of a common code cause between no-runner cancellations and package HTTP 503.
