# Browser snapshot frontend recovery candidate

## Objective

Repair the recurring pinned Debian snapshot HTTP 503/504 browser-image fetch failure without changing versions, timestamp, image digests, APT verification or native browser acceptance. This candidate starts at integrated main `f2c15cdcaa1c0755eb96e8c3de09078fc6b837a4`, not the earlier `a08b93d3dc32950917ed6ca5585d46b21761a7d3`. No merge, installation, publication or Phase 5B work is authorized.

## Methods and causality

Inspected attempt-specific job APIs for browser run [41863779087](https://github.com/99percentgrip/j%61rvis/actions/runs/41863779087): all three failed ARM image builds were on allocated runners. Attempt 1 hit snapshot HTTP 503, attempt 2 HTTP 503/504 and connection failures, attempt 3 HTTP 504 for `libnss3_3.87.1-1+deb12u4_arm64.deb`, `libmp3lame0_3.100-6_arm64.deb` and `libvorbisenc2_1.3.7-1_arm64.deb`. None ran subsequent ARM browser acceptance. Prior PR #34 installed bounded same-source retries; [its integrated main browser run 41969569598](https://github.com/99percentgrip/j%61rvis/actions/runs/41969569598) still failed twice, now on x86, after different pinned packages returned 503/504 despite successful ARM jobs. This proves that bounded retries alone do not cover sustained frontend unavailability; it is not evidence of a product browser failure.

Inspected the runtime Dockerfile: immutable base digests; `DEBIAN_SNAPSHOT=20261005T000000Z`; fixed headless-shell `154.0.8037.92-1~deb12u1`; three Debian snapshot suites with `check-valid-until=no`; APT signed Release and archive hash validation with `APT::Update::Error-Mode=any`. No floating package mirror is admissible. Probed both `snapshot.debian.org` and `snapshot-cloudflare.debian.org` with bounded `curl -Lf --max-time 30` on `/archive/debian/20261005T000000Z/dists/bookworm/InRelease` and the security InRelease. Successful bytes were **identical by SHA-256** across both: Debian `77737fa4b34f2693e982cc9ee35736816c35a7778fc2d326cc1bbf5b301fe1aa`; security `9e410c84fe36cff1047b97277bf37bfa3f8fff578eba22acda1f307cded000eb`. One security request to the primary returned HTTP 504 before a bounded successful retry; this is evidence of instability, not proof that the alternative can never fail. Both frontends provide the same timestamped signed metadata and content-addressed `/file/` redirects. The alternate uses the Debian-owned domain, not an unverified general mirror. APT remains the verifier of signatures and package hashes inside the image.

## Correction and red/green evidence

`.github/snapshot-apt.sh` retains two bounded (360-second) APT attempts per acquisition phase and per-request retries/timeouts. It now records the complete command diagnostic and refuses a frontend switch unless the failure is a bounded transport timeout or contains an HTTP 503/504 `E: Failed to fetch`, with no other `E:` class or integrity/signature alarm. A missing 404, hash mismatch or unsigned metadata fails without switching. After primary exhaustion it rewrites **only the host** of the existing timestamped sources from `snapshot.debian.org` to `snapshot-cloudflare.debian.org`, sleeps 10 seconds, and reruns authenticated update plus exact-version *download-only* acquisition. The final `apt-get --no-download install` is never retried: a maintainer-script failure cannot trigger a mirror switch. Both frontends exhausted still fail; image build never proceeds to acceptance on failure. No source version or Dockerfile image pin changes.

Red-first `python3 .github/test_snapshot_mirror.py -v` on pre-correction helper: `Ran 4 tests ... FAILED (failures=2)` (transport recovery and both-frontends exhaustion lacked a frontend switch). After correction: `Ran 7 tests ... OK`, including 503 fallback, bounded download-timeout fallback, missing 404 refusal, corrupt archive/unsigned metadata refusal, bounded double outage and offline dpkg failure without retry. Existing `python3 .github/test_browser_snapshot_install.py -v`: `Ran 5 tests ... OK`, preserving same-source transient retry, failure bounds and Dockerfile pin assertions. `sh -n .github/snapshot-apt.sh` passed. The canonical quality workflow enrolls both offline regression suites. `CARGO_BUILD_JOBS=2 timeout 1800 podman build --jobs 2 --format docker -f crates/j%61rvis-web-fetch/Dockerfile -t localhost/j%61rvis-browser-snapshot-candidate:local .` succeeded on local x86_64; image ID `0738e4c07fc7e1e973f80e534024a54d30110b86bfc0134ee1e0d17260de106b`, log showed `Setting up chromium-headless-shell (154.0.8037.92-1~deb12u1)` and `Successfully tagged ...`. The preceding uncorrected candidate build failed during the primary download with `Ign:` entries and no `E:` after the 360-second timeout, exposing the need to classify bounded download-only transport timeouts, rather than retrying package scripts. The successful local image used the available primary; it did not exercise alternate frontend in a real container. Fake-APT regressions cannot certify service availability; both real browser CI lanes remain mandatory.
